# 08: fyflow-plugin-sdk 0.11.0: the Plugin picks its build, the pool says what it holds

**What to build:** adopt `fyflow-plugin-sdk` 0.11.0, which ships what fyflow-app replied to our two requests
(`../fyflow-app-reply-resident-units.md`, `../fyflow-app-reply-plugin-picked-builds.md`). The SDK's own notes are
`../fyflow-app/packages/plugin-sdk/UPGRADING.md` ("0.10 to 0.11") and its README, "GPU builds: `variants` and
`pickVariant`".

When it's done:
- The Plugin picks its own build on each machine.
- A Profile can override that build, so one Flow can run some Nodes on the GPU and others on the CPU.
- The `cpu` build no longer holds the `gpu` unit.
- The Workers size their threads from what fyflow actually booked.

**Blocked by:** 06

**Status:** resolved

- [x] **Peer range:** `fyflow-plugin-sdk` `^0.11.0`, with the devDependency at `0.11.0`. Bump `fyflow-orchestration` and `fyflow-scheduler` to whatever the SDK 0.11.0 needs.
  - `pool.variants` is refused by older Hosts, so we don't keep 0.9 or 0.10 support.
  - Nothing is published yet, so no one is left behind.
- [x] **`python.pickVariant` in `plugin.ts`,** using our own NVIDIA check. The SDK has no helpers for it.
  - **Linux:** read `/proc/driver/nvidia/version`. `cuda` if the driver is at least 580.65.06 (CUDA 13's). With no version file, look for `libcuda.so.1` in the usual places, and if it's there, take `cuda` without a version check.
  - **Windows:** `cuda` if `%SystemRoot%\System32\nvcuda.dll` exists and its driver version is at least 580.88 (CUDA 13's).
    - Read the version from the DLL's `VS_FIXEDFILEINFO`: find the signature `0xFEEF04BD`, then read the file version. No npm dependency.
    - The NVIDIA driver version is the last digit of the third part followed by the fourth part. For example, `32.0.15.6094` → `560.94`.
    - If the version can't be read, a present DLL counts as `cuda`.
  - **Otherwise:** `directml` on Windows, else `cpu`. Never throw; on any error, return `cpu`.
  - Keep the detection in its own small module, with tests that use fake file contents. Don't touch the real machine in `pnpm check`.
- [x] **Holds per build:** both Node Types' pools get `variants: { cpu: { residentGroups: { cpu: 4 } } }`, so the `cpu` build doesn't hold `gpu`.
  - Use the existing `RESIDENT_GROUPS` constant, or a `cpu`-only one beside it.
- [x] **The Worker reads `config["host"]["pool"]`:**
  - **Threads:** onnxruntime's thread count is `residentGroups.cpu.cost`, falling back to `CPU_UNITS`.
  - **Thread pool:** ClassifyImage's blocking thread pool is sized from `maxConcurrentTasks`, falling back to `TASKS_AT_ONCE`.
  - **Remove `pool.holds`:** take out the guess in `_cpu_units` and the fake `Pool(holds=…)` in the tests.
  - **GPU choice stays the same:** the device still comes from `pool.grants["gpu"]`, and providers still come from what the installed build offers.
  - **Log the build:** read `config["host"]["variant"]` only to include it in the session's provider line on stderr.
- [x] **No `python.accelerator` left anywhere:**
  - README, spec, `plugin.ts` comments and `devices.py`'s docstring.
  - The README should say instead:
    - the Plugin picks `cuda`, `directml` or `cpu` itself;
    - a person can override it per Profile (the Default Profile for every Node) on the Profiles page;
    - a CUDA build with a broken driver falls back to the CPU;
    - the `cpu` build holds no `gpu`.
  - Remove the README's caveat that the `gpu` unit is held on `cpu` too.
- [x] **No `host` start-up field** (the SDK refuses one). We have `batchSize` and `modelDir`; a test should guard this.
- [x] **Docs:**
  - In `../todo.md`, mark "GPU or CPU per node" and the fyflow-app requests as done.
  - Add a todo item for the Allowed roots opt-in (`roots: true`, ADR-0030). It's out of scope here.
- [x] **Verified by hand on a Host** (fyflow-app at the 0.11.0 commit), with no `FYFLOW_PYTHON_ACCELERATOR`:
  - the Plugins page shows the picked build (`cuda` on this machine);
  - a Profile set to `cpu` runs on the CPU and doesn't hold `gpu`.

## Changed while building it (2026-11-12)

- **Driver minimums are CUDA 13's,** not CUDA 12's: 580.88 on Windows (`nvcuda.dll` 32.0.15.8088) and 580.65.06 on Linux. The lock pins `onnxruntime-gpu` 1.31.1, built for CUDA 13, so an older driver would have picked `cuda` and then fallen back to the CPU when DirectML could have run.
- **Decisions the ticket left open:**
  - A Linux version file whose version can't be parsed counts as `cuda`, as an unreadable DLL does on Windows. A DLL that can't be read at all (for example, access denied) gives `cpu`.
  - The `libcuda.so.1` search also covers `/usr/lib/aarch64-linux-gnu`, `/usr/lib` and `/usr/lib/wsl/lib` (WSL).
  - `pick-build.ts` is copied into the Plugin folder by `pnpm plugin-folder`, guarded by `test/plugin-folder.test.ts`.
- **SDK dependencies:** `fyflow-orchestration` 0.14.0 and `fyflow-scheduler` 0.7.0 already fit SDK 0.11.0, so they are unchanged.
- **Verified by hand** on fyflow-app at its 0.11.0 commit, with no `FYFLOW_PYTHON_ACCELERATOR`:
  - The Plugins page showed `cuda`, "picked".
  - A "CPU" Profile with `variant: cpu` made the Host sync both builds. In one two-Node Flow, the default Node ran on CUDA (gpu unit 0) and the CPU-Profile Node on the CPU, both with 4 threads from `host.pool`, and both tagged the image `anime`.
  - The `cpu` build doesn't hold the gpu unit. The Flow took 0.23 s with the CPU Profile on `cpu`, against 12 to 20 s with it on `cuda`, where the second Node waits for the first Node's pool to release the unit.
